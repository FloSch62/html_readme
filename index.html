How the new direct c9s builds a lab.

We will follow two routers and one cable—from YAML, to Pods, to traffic crossing Kubernetes workers—and stop at each part to see what it does.

The short version

You describe routers and cables. c9s works out how each router must start, Kubernetes runs the real router containers, and a privileged sidecar inside each Pod connects the cables and the management network. Nothing runs on the worker itself.

The router is the PodThe NOS image is a normal Kubernetes container.
No Docker, no daemonNo dockerd inside, and no agent on any worker. All networking is Pod-local.
One cable = one LinkLinks stay separate from Nodes and can change on their own.
Management like containerlabAllocated addresses on one shared L2 management domain—172.20.20.0/24 by default.
Checks before readyFiles, wiring, containers, image health, TCP, and SSH can all be checked.

“Direct” does not mean “one container and nothing else.” c9s still needs small helpers to prepare config files, create interfaces, and check progress. The important part is that these helpers never start another hidden router, and they never leave the Pod: since the host-endpoint daemon was removed, no c9s component runs on the worker at all. The router you see in the Pod is the real one, and everything that connects it lives and dies with that Pod.
Who runs the router?

Kubernetes does

The NOS image sits in Pod.spec.containers. Normal kubectl logs, exec, status, and metrics go straight to it.

Who knows the vendors?

Containerlab still does

c9s uses the Containerlab Go package to learn how SR Linux, cEOS, SR OS, Linux, and other kinds need to start. c9s does not keep a second list of vendor tricks.

What if it cannot map something?

It stops early

If a Docker-only option has no safe Kubernetes version, c9s reports the exact problem before creating the router Pod. It does not quietly drop the setting.

How this branch got here — four archived OpenSpec changes, in order:
1
direct-node-pods

The router becomes the Pod

Removed the nested launcher runtime. Devices run as normal containers from a recorded, checked Containerlab plan. Cross-worker cables still used a per-worker daemon at this point.

2
sidecar-mgmt-interposition

The daemon is deleted

The Pod’s connectivity sidecar takes over everything: an interposed management interface with a real allocated address, in-Pod VXLAN cables, and host Links. internal/hostendpoint no longer exists.

3
management-l2-mesh

Management becomes one L2 domain

Each Pod bridges its management legs onto a mesh VTEP. Devices reach each other’s management addresses directly, exactly like containerlab’s management bridge.

4
retire-launcher-era-surface

The old vocabulary goes

LauncherProfile → NodeProfile, the connectivity selector field is removed, upgrade-compat code is deleted, and launcher-era naming is purged. One clean 0.9 breaking cut.

02 · Meet the pieces

A Node is a router. A Link is a cable.

Put the objects for one lab in one Kubernetes namespace. Think of that namespace as the room where the lab is built.

N
The box

Node

One logical router or host. The Node name becomes the device name. Its spec looks much like one node from a Containerlab file: kind, image, startup config, commands, files, and ports.

L
The cable

Link

Two ends, for example r1:e1-1 and r2:e1-1. The Link controller checks both ends and gives cross-Pod Links a tunnel number.

P
The house rules

NodeProfile

Shared Pod policy, referenced from a Node via spec.profileRef: CPU and memory, scheduling, image pull secrets, persistence, exposed ports, management addressing (mgmt), and probes. Renamed from the launcher-era LauncherProfile in this branch.

T
The shortcut

Topology

If you prefer one Containerlab-style file, use a Topology. Its controller splits that file into a profile, Nodes, and Links. After that, the same Node and Link controllers take over.

Why split Nodes and Links?

Large labs do not pile into one object

Each Node carries only its own setup. Each Link carries one cable. A router watches only the Links that touch it instead of scanning the whole lab. This needs Kubernetes 1.31 or newer.

one Node per deviceone Link per cablewatch only nearby Links
When devices must share a network stack

Several containers can live in one Pod

network-mode: container:<primary> puts the second Node in the primary Node’s Pod. Multi-container chassis work in a similar way: one logical Node can become several visible containers.

one shared Pod networkeach Node still has status
Two small rules matter: if a Node’s profileRef names a NodeProfile, that profile must exist in the same namespace—if it is missing, c9s waits and reports NodeProfileResolved false. And Links no longer carry a connectivity field: there is exactly one cross-Pod transport now, so there is nothing left to select.

What is reused

Containerlab’s kind knowledge

The kind registry, node objects, config generation, component layout, endpoint hooks, health checks, and save behavior stay in the Containerlab package. c9s does not copy that vendor logic.

What is replaced

The runtime underneath it

Containerlab sees a small runtime that looks familiar, but it records requests instead of talking to Docker. A tiny local shim supports only planned docker exec-style calls; there is no daemon or socket.

Who pulls the image

The kubelet, once

c9s reads the OCI manifest and config to learn the digest, command, environment, and health check. A recorded PullImage does no download. The kubelet pulls the real layers for the Pod.

The important boundary: planning is not blindly replaying a shell script. Later helpers rebuild the same Containerlab kind from the saved input, call the right hook for that moment, and reject work that does not match the accepted plan.
One path for every kind

No vendor switch in c9s

The same recorder handles every imported kind. If a future Containerlab kind asks for operations c9s already understands, it uses the same path without new vendor code.

Repeatable

Same input, same plan

Image digests, file information, certificates, interfaces, and settings are part of the input. Running the planner again must produce the same plan.

Safe place to run package code

The planner cannot launch anything

It has no Docker or CRI socket, no host path, no Kubernetes token, and no privileged network access. Its NetworkPolicy denies everything—including DNS—unless a declared URL fetch needs a narrow exception, and it has a 300-second deadline. It can describe work, not perform it on the worker.

What the recorder allows vs. blocks

A short whitelist, a hard wall

Recorded and later realized: PullImage, CreateContainer, StartContainer, Exec, file copies, and stdin writes. Everything else—CreateNet, DeleteContainer, GetRuntimeSocket, log streaming, and friends—fails the plan immediately with “imported code reached a forbidden runtime boundary.” A kind that needs an unmapped operation is stopped at planning, never half-run.

The docker that isn’t

An exec-only shim wearing Docker’s name

The recorder answers GetName() with "docker", and inside the Pod, docker and podman are symlinks to the c9s helper. The shim accepts exactly one verb—exec—and only against the plan-declared target container. It runs a real PTY and filters terminal-query escape sequences, which is enough for kind packages that screen-scrape their own CLI, and nothing more. There is no socket to find.

Where the plan lives

An immutable, digest-named ConfigMap

<node>-plan-<12 hex of its digest>, key plan.json, marked immutable, capped at 768 KiB. Every byte value of every pull Secret is registered as sensitive first: a plan or input that would contain one is refused before it is ever stored. The mutable sibling is the small connectivity-revision ConfigMap the sidecar polls.

When Nodes share networking

Several devices can share one Pod

network-mode: container:<primary> puts each grouped Node in the primary Node’s Pod, so they share the same network namespace. They still keep separate status and Services.

When one Node has parts

One device can need several containers

A chassis may have a controller and cards. Containerlab tells the plan about those components, and c9s puts all of them in the Pod. The Node is ready only when every required part is ready.

Small quality-of-life detail: plain kubectl logs and kubectl exec choose the main device container. Add -c only when you want a card, a grouped device, or the connectivity helper.
05 · Links & fabric

The r1—r2 cable never leaves the Pods.

r1 and r2 always see an ordinary Ethernet interface. Every cross-Pod cable has the same hidden shape now: a veth pair inside each Pod, stitched to an in-Pod VXLAN tunnel endpoint that rides the ordinary Pod network. Same worker or different workers—one path, no special cases.

Why the tunnel can finally live inside the Pod: the old worry was that a NOS renames the Pod’s primary interface or strips its IP and routes, cutting off any tunnel built on it. Interposition (next section) removes that hazard: the sidecar renames the CNI interface to c9s0 before the device ever starts, and the device is handed a synthetic eth0 instead. The device can do whatever it likes to the interfaces it sees—the Kubernetes underlay it never sees stays intact, so the VXLAN endpoints on top of it stay reachable. That is what made the per-worker daemon unnecessary.

A veth pair dies when either end’s namespace dies. So when the Pod is deleted—gracefully or by force—the worker-side end vanishes with it. The old daemon needed a 15-second orphan sweep to guarantee this; the new design gets it for free, by construction.

Naming you will see in ip link

Everything sidecar-owned says c9s

c9s0 is the preserved CNI interface. Per cable: c9ss… stitch leg, c9sx… VTEP, c9sh… a host-Link leg in transit. Management adds c9sr0, c9sb0, c9sm0, c9sd0, c9sg0 (next section).

Every interface has an owner

UIDs travel into Linux

c9s writes ownership into interface aliases and converges only what it owns. A new object with the same name cannot accidentally take over an old interface, and a retried update reaches the same state.

Hardening baked in

Checksums and MTU are handled

TX checksum offload is disabled on the synthetic legs (VXLAN-stitched frames must carry real checksums), and the fabric MTU is clamped to the underlay minus VXLAN overhead.

VXLAN, precisely

Port 14789, budgeted VNIs, and a stitch that is not a bridge.

Everything the sidecar builds for one cable fits on one screen. The commands below are the shell equivalent of what it does through netlink—idempotently, re-checked every second.

shell equivalent · one cross-Pod cable (VNI 4242) + one mesh peer
# device leg + sidecar stitch leg (suffix = first 8 hex of sha256 over "<Link UID>/a")
ip link add e1-1 type veth peer name c9ss3f9c01ab

# the cable's tunnel endpoint: strictly unicast, no learning, no FDB
ip link add c9sx3f9c01ab type vxlan id 4242 \
    local 10.244.2.134 remote 10.244.7.21 \
    dstport 14789 nolearning

# the stitch: tc steals every frame on one side and pushes it out the other
tc qdisc  replace dev c9ss3f9c01ab clsact
tc filter replace dev c9ss3f9c01ab ingress prio 42 matchall \
    action mirred egress redirect dev c9sx3f9c01ab
tc filter replace dev c9sx3f9c01ab ingress prio 42 matchall \
    action mirred egress redirect dev c9ss3f9c01ab

# software checksums on both legs -- offloaded (empty) checksums would be
# silently dropped when mirred pushes frames into a VXLAN device
ethtool -K e1-1 tx off

Why UDP 14789, not 4789

The lab keeps the real port

The number is pinned once (VXLANServicePort = 14789) and used everywhere: cable VTEPs, mesh VTEPs, the -vx Services, the mesh Service. The repo keeps no written rationale—the 2023 commit says only “use 14789 instead of 4789”—but the effect is easy to state: IANA’s 4789 stays free. NOS dataplanes terminate real VXLAN/EVPN on 4789, and CNIs use 4789 or 8472 for their own encapsulation, so a lab can run genuine VXLAN inside the devices while c9s carries it on a port nobody else claims.

A budgeted VNI space

Cables below 16 M, meshes above

Cross-Pod Links draw lowest-free from a cluster-wide space of 1–16,000,000 (namespaces used to share worker namespaces, and the ceiling simply stayed). VXLAN’s real maximum is 16,777,215—the slice above the ceiling, 16,000,001–16,777,000, is reserved: a namespace’s mesh VNI is 16,000,001 + sha256("c9s-management-mesh/<ns>") mod 777,000. A cable and a mesh can never collide, by construction rather than by coordination.

Allocation lifecycle

Sticky, deterministic, freed by absence

An accepted Link keeps its VNI across rewires—that is what makes a rewire a live tunnel move instead of a re-allocation. A collision is settled without clocks: the lexically smaller namespace/name keeps the number, the other reallocates. Deleting a Link frees its VNI by pure absence: no finalizer, no free-list, just the next lowest-free scan. Same-Pod and host Links get 0—no tunnel exists for them at all.

06 · Management plane & mesh

r1 gets a real management network, not a borrowed Pod IP.

The Pod address is no longer r1’s identity. The controller allocates a containerlab-style management address, the sidecar interposes a synthetic management interface carrying it before the NOS starts, and every Pod in the namespace is bridged into one shared L2 management domain—exactly what containerlab’s management bridge gives you on Docker.

The trick in one sentence: the sidecar renames the CNI-created interface to c9s0 and keeps it for Kubernetes transport, then hands the device a freshly made veth eth0 that carries the allocated management address (say 172.20.20.11/24). The NOS adopts it exactly as it would a physical management port—lease synthesis, mgmt0.0 addressing, SSH, all of it—while the Kubernetes underlay stays untouchable one interface away. This pattern (validated in spikes against unmodified SR Linux, SR-SIM, and cEOS) is what the change calls interposition.

Where the address comes from

Allocated, never improvised

The NodeProfile’s mgmt policy (subnets, gateway, static mgmt-ipv4/mgmt-ipv6) wins when present. Without one, c9s allocates from containerlab’s default 172.20.20.0/24 with the gateway at the first usable address. Management config renders at plan time through each kind’s own containerlab templates; the only runtime-completed input left is DNS resolver discovery from the Pod.

Why exposure still works

NAT at the gateway hop

The device listens on its management address, but the cluster only knows the Pod IP. The sidecar’s c9s-interposition nftables table DNATs declared inbound ports from the Pod address to the management address and SNATs outbound management traffic back to the Pod address. Its hook priorities (−110/90) sit ahead of anything a device programs into its own iptables—proven against cEOS, which programs plenty.

Why kubectl keeps working

Transport is protected

A sidecar-owned policy routing table (20000) carries Kubernetes transport, selected by three rules: anything entering via the gateway leg, Pod-sourced traffic such as VTEP encapsulation, and traffic to the Pod’s own management address. A device may wipe the main routing table; probes, logs, and tunnels keep flowing.

The translation

A NAT table the device cannot out-rule.

The whole translation fits on one screen. The sidecar rebuilds the c9s-interposition table atomically on every pass—flush and re-add in a single kernel transaction—so it is always exactly this, no matter what the NOS has meanwhile done to its own iptables.

nft list table ip c9s-interposition · representative (Pod IP 10.244.2.134, device 172.20.20.11)
table ip c9s-interposition {            # netns-scoped: exists only inside this Pod
  chain dstnat {
    type nat hook prerouting priority -110; policy accept;
    # one DNAT rule per declared inbound port: Pod identity in, device identity out
    ip daddr 10.244.2.134 tcp dport 22    dnat to 172.20.20.11:22
    ip daddr 10.244.2.134 tcp dport 830   dnat to 172.20.20.11:830
    ip daddr 10.244.2.134 tcp dport 57400 dnat to 172.20.20.11:57400
    ip daddr 10.244.2.134 udp dport 161   dnat to 172.20.20.11:161
    # ... every other declared port, same shape
  }
  chain srcnat {
    type nat hook postrouting priority 90; policy accept;
    # shape 1: anything from the management subnet leaving for the cluster
    oifname "c9s0" ip saddr 172.20.20.0/24 masquerade
    # shape 2: locally-originated flows get their NAT verdict on the device leg,
    #          and intra-subnet (mesh) destinations are explicitly never translated
    oifname "eth0" ip saddr 172.20.20.11 ip daddr != 172.20.20.0/24 snat to 10.244.2.134
  }
}
Why −110 and 90

Ahead of iptables, without touching it

Every x_tables NAT chain sits at a fixed priority: PREROUTING at −100, POSTROUTING at 100. By hooking dstnat at −110 and srcnat at 90, the sidecar’s verdict always lands first—no rule inside the device’s own iptables is read, reordered, or deleted. Proven against cEOS, which programs plenty of its own; its FORWARD chain conveniently accepts what interposition forwards, so no filter chain is needed at all.

Which ports get DNATed

Three sources, one union

Declared topology ports:, the image’s EXPOSE list, and—unless the profile sets disableAutoExpose—the auto-expose defaults: TCP 21, 22, 23, 80, 443, 830, 5000, 5900, 6030, 9339, 9340, 9559, 57400 and UDP 161. Ports of Pod-mates (grouped Nodes) claim their number without translation, so a declared port can never shadow a sibling’s listener. Today the Pod port always equals the device port.

What is never translated

The mesh speaks with real addresses

Device-to-device management traffic stays untranslated: the daddr != 172.20.20.0/24 exclusion covers locally-bound flows, and mesh traffic never exits via c9s0 anyway. When r1 pings r2’s .12, r2 sees .11—exactly containerlab’s bridge behavior. The table is IPv4-only by design: an IPv6 management address is put on the device leg untranslated.

The mesh

One flat management LAN across every Pod.

Interposition alone would leave each Pod a private island of 172.20.20.0/24. Real labs hardcode peer management addresses—gnmic targets, syslog collectors, a plain ping. So each Pod’s bridge also carries a mesh VTEP (c9sm0), and the whole namespace becomes one broadcast domain: ARP resolves the peer device’s actual MAC, and any protocol runs device-to-device in both directions.

Peer discovery

A Service, not a plan

Peers are deliberately not plan data—a planned peer list would recreate every Pod whenever a Node joins or leaves. Instead one namespace-scoped headless Service (c9s-management-mesh, not-ready addresses published) lists all member Pods; each sidecar resolves it on its tick and reconciles head-end-replication FDB entries exactly. Scale-out and scale-in restart nothing.

VNI allocation

Collision-free by construction

The mesh VNI is derived from the namespace name into the range above 16,000,000—the ceiling of the Link allocator—so a management mesh can never collide with any cable’s tunnel ID. The gateway MAC (02:c9:…) is derived the same way, identical in every Pod of the namespace.

Gateway containment

Isolation, not netfilter

The gateway port and mesh port are both isolated bridge ports, so gateway↔mesh traffic is structurally impossible: every Pod answers the gateway address locally with the same deterministic MAC, and no gateway frame ever crosses the mesh. This uses core bridge port isolation because some kernels (WSL2 among them) ship no bridge netfilter.

Kernel gotchas, solved

ARP flux and br_netfilter

arp_ignore=1 on every mesh element (device leg included) keeps a single gateway ARP from getting three answers. And because Kubernetes nodes load br_netfilter, the sidecar disables bridge-nf-call-* inside the Pod namespace so bridged frames are not re-run through conntrack—found and fixed during cluster conformance.

What deliberately does not happen: the management prefix is not routed off-cluster (reach devices from outside via their exposed Services), IPv4 is the translated path (an IPv6 management address is assigned to the device leg untranslated), and the mesh carries intra-topology management traffic only. Name-based reachability coexists throughout: every Node keeps its namespace-local Services, and declared aliases add extra headless names.

The slurpeeth story

The TCP tunnel was not defeated. It was made redundant.

slurpeeth was a userspace transport that stuffed Ethernet frames into TCP streams—an experimental alternative to VXLAN for clusters whose underlay clipped or fragmented encapsulated frames. Its removal took four distinct steps, and the reasoning is worth reading in order.

Born as an experiment (Dec 2023 – Jan 2024)Merged as feature PR #90: a per-link TCP tunnel daemon (carlmontanari/slurpeeth) in every launcher, on TCP 4799, selectable via the connectivity field—first on a Connectivity CRD, later on Link and Topology directly. Its purpose: dodge VXLAN MTU and fragmentation trouble.
Ported to direct Pods anyway (2026-08-19)The direct change first reimplemented it as a sidecar-supervised child process—about 1,700 lines—because the pinned library’s process-global manager could not offer a resettable, race-free reconnect lifecycle inside a Pod.
Deleted the same day, together with the whole in-Pod fabricThe real discovery: kinds that own the Pod’s primary interface (SR Linux renames it and strips its address) leave the namespace without underlay routes—so any transport terminating there dies, VXLAN and TCP alike. The fabric moved to the worker host namespace, and both flavors became aliases of one controller-selected realization. From this moment connectivity: slurpeeth was accepted input that changed nothing.
Interposition dissolves the original problem (2026-08-21)The fabric comes back in-Pod—but on the preserved c9s0 underlay the device can never touch. MTU is now clamped below the underlay (no fragmentation to dodge), and the CNI carries plain Pod-to-Pod UDP wherever Pod traffic works at all. Every case slurpeeth existed for is covered by the one remaining transport.
The selector goes (2026-08-21)The retire change, verbatim: “With slurpeeth retired to an alias of the VXLAN realization, connectivity selected nothing while still constraining behavior (a uint16 VNI clamp, a dead TCP/4799 fabric port) and shipping false CRD prose. The field is removed rather than frozen at a single value; a future second transport should design its own selector.” The dependency left go.mod with the launcher.
The moral: slurpeeth was not removed because it failed. It was removed because interposition changed the terrain—once the underlay is preserved and the MTU is clamped, a selector choosing between two identical outcomes is pure API debt. That is also the pattern of every row in the table above: the direct architecture did not defeat these components; it removed the conditions that made them necessary.

10 · Security boundaries

The powerful parts are small and easy to point at.

Creating interfaces, routing tables, and NAT rules needs root-like Linux rights. c9s keeps those rights in one fixed helper—the connectivity sidecar—and scopes them to the Pod it lives in. The planner and the router container never get them.

Planner Pod

It can describe, not launch

No Kubernetes token, host directory, Docker/CRI socket, or privileged networking. It has a read-only root and private scratch. Network access is denied unless a declared file fetch needs a narrow exception.

Router container

No Kubernetes identity

automountServiceAccountToken: false. The NOS does not receive cluster credentials, the worker network namespace, or a container-runtime socket.

Connectivity sidecar

Power inside this Pod only

It is privileged so it can make interfaces, bridges, VTEPs, routing rules, and nftables state—but everything it creates lives in its own Pod’s network namespace and follows the accepted plan. It holds no Kubernetes write credentials and talks to no daemon.

The worker

Nothing runs there

No DaemonSet, no host socket, no host-network c9s process. The only host touch left is a read-only worker network-namespace handle, mounted into the sidecar only when the topology declares host Links, used solely to place one end of a veth pair.

Branch note: the nested launcher runtime is gone entirely—there is no mode to select and no fallback. 0.9 ships as one breaking cut: the documented upgrade path is a full uninstall and reinstall, old LauncherProfile/connectivity manifests fail validation with named fields, and workers that ran the previous daemon may need a one-time cleanup of stale daemon-era interfaces (or a reboot).

r1-r2

The cable ignores placement

Wherever the two Pods land, the cable is a per-Pod veth stitched to an in-Pod VXLAN VTEP using the Link’s allocated VNI. r1 and r2 see the same plain Ethernet interfaces either way.

r1-host

The worker gets one end

host is a reserved endpoint name. r1’s sidecar creates the eth2 ↔ c9s-r1-host veth pair inside the Pod and moves the named end into the worker namespace; deleting the Pod deletes both ends.

What appears alongside

Services and the mesh

Each Node gets a headless <name>-vx discovery Service and its exposed-port Service targeting the Pod directly. The namespace also gets one c9s-management-mesh Service, and both routers get management addresses on the same shared subnet—so r1 can ping r2’s management address out of the box.

The whole story in one breath

Containerlab knows the device. Kubernetes runs it. The sidecar wires it.

You create Nodes and Links. c9s loads the real Containerlab kind, records how that device wants to run, checks the recording, and turns it into a normal Pod. Inside that Pod, a privileged sidecar preserves the CNI interface as c9s0, hands the device a synthetic eth0 carrying a controller-allocated management address, bridges every Pod of the namespace into one L2 management mesh, and realizes each cable as a stitched in-Pod VXLAN tunnel between Pod IPs. Nothing runs on the workers. Containerlab’s own post-start, endpoint, health, and save hooks are still used, but every action is checked against the saved plan. UIDs own the cables; digests own the build; the Pod’s lifetime owns the cleanup.
