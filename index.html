Clabernetes · direct runtime

How the new direct c9s builds a lab.

Wie das neue direct c9s ein Lab baut.

We will follow two routers and one cable, from YAML to Pods to traffic crossing Kubernetes workers, and stop at each part to see what it does.

Wir folgen zwei Routern und einem Kabel — vom YAML über die Pods bis zum Traffic zwischen Kubernetes-Workern — und halten an jedem Bauteil an, um zu sehen, was es tut.

The short version
Die Kurzfassung

You describe routers and cables. c9s works out how each router must start, Kubernetes runs the real router containers, and a privileged sidecar inside each Pod connects the cables and the management network. Cross-Pod cables ride a c9s-owned UDP wire between the sidecars, so any link MTU works on any cluster and pulling a port propagates real loss of carrier. No c9s daemon or host-network process is installed on the worker.

Man beschreibt Router und Kabel. c9s ermittelt, wie jeder Router starten muss, Kubernetes betreibt die echten Router-Container, und ein privilegierter Sidecar in jedem Pod verbindet die Kabel und das Management-Netz. Pod-übergreifende Kabel laufen über eine c9s-eigene UDP-Leitung zwischen den Sidecars — dadurch funktioniert jede Link-MTU auf jedem Cluster, und das Ziehen eines Ports erzeugt echten Carrier-Verlust. Auf dem Worker wird kein c9s-Daemon oder Host-Network-Prozess installiert.

Why split Nodes and Links?

Large labs do not pile into one object

Each Node carries only its own setup. Each Link carries one cable. A router watches only the Links that touch it instead of scanning the whole lab. This needs Kubernetes 1.31 or newer.

Warum Nodes und Links trennen?

Große Labs stapeln sich nicht in einem Objekt

Jeder Node trägt nur sein eigenes Setup. Jeder Link trägt ein Kabel. Ein Router beobachtet nur die Links, die ihn berühren, statt das ganze Lab zu durchsuchen. Das braucht Kubernetes 1.31 oder neuer.

Several containers can live in one Pod

network-mode: container:<primary> puts the second Node in the primary Node’s Pod. Multi-container chassis work in a similar way: one logical Node can become several visible containers.

Wenn Geräte einen Netzwerk-Stack teilen müssen

Two small rules matter: if a Node’s profileRef names a NodeProfile, that profile must exist in the same namespace; if it is missing, c9s waits and reports NodeProfileResolved false. And Links no longer carry a connectivity field: there is exactly one cross-Pod transport now, so there is nothing left to select.

What is replaced

The runtime underneath it

Containerlab sees a small runtime that looks familiar, but it records requests instead of talking to Docker. A tiny local shim supports only planned docker exec-style calls; there is no daemon or socket.

One path for every kind

No vendor switch in c9s

The same recorder handles every imported kind. If a future Containerlab kind asks for operations c9s already understands, it uses the same path without new vendor code.

Derselbe Recorder behandelt jedes importierte Kind. Verlangt ein künftiges Containerlab-Kind nur Operationen, die c9s schon versteht, nutzt es denselben Pfad ohne neuen Herstellercode.

Repeatable

Same input, same plan

Image digests, file information, certificates, interfaces, and settings are part of the input. Running the planner again must produce the same plan.

Wiederholbar

Gleicher Input, gleicher Plan

Image-Digests, Dateiinformationen, Zertifikate, Interfaces und Einstellungen sind Teil des Inputs. Ein erneuter Planner-Lauf muss denselben Plan ergeben.

Safe place to run package code

The planner cannot launch anything

It has no Docker or CRI socket, no host path, no Kubernetes token, and no privileged network access. Its default-deny NetworkPolicy blocks network traffic when enforced by the CNI. The controller supplies external file data, and each request has a maximum 300-second deadline. It can describe work, not perform it on the worker.

Sicherer Ort für Paket-Code

Der Planner kann nichts starten

Kein Docker- oder CRI-Socket, kein Host-Pfad, kein Kubernetes-Token, kein privilegierter Netzzugriff. Seine Default-Deny-NetworkPolicy blockiert Netzwerkverkehr, sofern das CNI sie durchsetzt. Externe Dateiinhalte liefert der Controller; jede Anfrage hat ein Limit von maximal 300 Sekunden. Er kann Arbeit beschreiben, aber nicht auf dem Worker ausführen.

What the recorder allows vs. blocks

A short whitelist, a hard wall

Recorded and later realized: PullImage, CreateContainer, StartContainer, Exec, file copies, and stdin writes. Everything else (CreateNet, DeleteContainer, GetRuntimeSocket, log streaming, and so on) fails the plan immediately with “imported code reached a forbidden runtime boundary.” A kind that needs an unmapped operation is stopped at planning, never half-run.

Was der Recorder erlaubt und blockt

Kurze Whitelist, harte Wand

Aufgezeichnet und später umgesetzt: PullImage, CreateContainer, StartContainer, Exec, Dateikopien und stdin-Writes. An immutable, digest-named ConfigMap

What it is

A restartable init container

It runs the fixed c9s image (never the NOS image) as a native Kubernetes sidecar: an init container with restartPolicy: Always. Its startup probe holds the device containers back until local interfaces are prepared, without waiting for remote peer health; after that it keeps running beside them. It is privileged for Pod networking and receives a read-only-mounted worker network-namespace handle for host-Link placement and imported endpoint hooks. A projected service-account token gives it namespace-scoped, read-only access to Links, Pods, and Pod logs; the plan-scoped log broker validates its own Pod UID and allowlists target containers. It has no Kubernetes write credentials and talks to no daemon; application containers receive neither the token nor the host handle.

Was er ist

Ein neustartbarer Init-Container

Er läuft mit dem festen c9s-Image (nie mit dem NOS-Image) als nativer Kubernetes-Sidecar: ein Init-Container mit restartPolicy: Always. Seine Startup-Probe hält die Geräte-Container zurück, bis die lokalen Interfaces vorbereitet sind, ohne auf die Gesundheit entfernter Peers zu warten; danach läuft er neben ihnen weiter. How it works

A one-second reconcile loop, plus a live wire pump

Its mounted inputs are the immutable plan/input pair and a small mutable revision ConfigMap. Services provide peer discovery, while the read-only Kubernetes identity supports the plan-scoped application log broker. Every second it re-checks state through netlink and converges what drifted; a device may rename or move interfaces, wipe routes, or program iptables, and the sidecar re-asserts only the state it owns. In the same process it runs the fabric wire pump: one UDP socket, packet sockets on the cable legs, heartbeat and carrier timers.

Wie er arbeitet

What happens to a large frame

Worked example: 9000-byte payload over a 1480-byte Pod network

r1 sends a 9014-byte Ethernet frame (9000-byte IP packet + 14-byte header) into its 9500-MTU e1-1. The sidecar’s packet socket picks it up on the wire leg and computes the fragment payload from the locally observed underlay MTU: 1480 − 28 (IP+UDP) − 22 (wire headers) = 1430 bytes per fragment. The frame becomes ⌈9014 / 1430⌉ = 7 datagrams — six carrying 1430 bytes, the last carrying 434 — all stamped linkID 42, frameID N, fragIndex 0…6 of 7, totalLen 9014, sent back-to-back with one batched sendmmsg call. r2’s sidecar collects the seven pieces (any order, duplicates ignored), verifies the byte count, and injects the original 9014-byte frame out of its wire leg. r2 receives exactly what r1 sent. A 100-byte frame skips all of this: one fragment, one datagram.

Why this design

Loss stays loss — deliberately

If any fragment of a frame is lost, the whole frame is dropped after a 100 ms reassembly window. Nothing is retransmitted, nothing is acknowledged, ever. That sounds harsh, but it is the point: a TCP-style wire would silently repair loss and add head-of-line blocking, and then loss testing, BFD timers, and convergence measurements inside the lab would measure the wire instead of the network. One consequence to know: a jumbo frame split into 7 fragments dies if any one of them dies, so jumbo loss rate ≈ 7× the underlay loss rate. Reassembly is memory-capped at 64 frames in flight per link, and mixed-MTU workers need no coordination — each sender fragments to its own underlay, reassembly does not care.

Warum dieses Design

Verlust bleibt Verlust — absichtlich

Geht irgendein Fragment eines Frames verloren, wird der ganze Frame nach einem 100-ms-Reassembly-Fenster verworfen. Nichts wird neu übertragen, nichts bestätigt — nie. Das klingt hart, ist aber der Punkt: Eine TCP-artige Leitung würde Verlust stillschweigend reparieren und Head-of-Line-Blocking hinzufügen — Verlusttests, BFD-Timer und Konvergenzmessungen im Lab würden dann die Leitung vermessen statt das Netz. Eine Konsequenz sollte man kennen: Ein in 7 Fragmente zerlegter Jumbo-Frame stirbt, wenn eines davon stirbt — die Jumbo-Verlustrate ist also ≈ 7× die Underlay-Verlustrate. Reassembly ist auf 64 Frames in Arbeit pro Link speicherbegrenzt, und Worker mit unterschiedlichen MTUs brauchen keine Abstimmung — jeder Sender fragmentiert auf seinen eigenen Underlay, dem Zusammensetzen ist das egal.

Allocation lifecycle

Kept on rewires, freed on delete

An accepted Link keeps its id across rewires; that is what makes a rewire a live move instead of a re-allocation. The slurpeeth story
Die slurpeeth-Geschichte

Why slurpeeth was removed.

Warum slurpeeth entfernt wurde.

slurpeeth was a userspace transport that stuffed Ethernet frames into TCP streams: an experimental alternative to VXLAN for clusters whose underlay clipped or fragmented encapsulated frames. Its removal happened in steps — and the final step is an irony worth savoring.

slurpeeth war ein Userspace-Transport, der Ethernet-Frames in TCP-Streams stopfte: eine experimentelle Alternative zu VXLAN für Cluster, deren Underlay gekapselte Frames beschnitt oder fragmentierte. Seine Entfernung geschah in Schritten — und der letzte Schritt ist eine Ironie, die man auskosten darf.

Born as an experiment (Dec 2023 to Jan 2024)Merged as feature PR #90: a per-link TCP tunnel daemon (carlmontanari/slurpeeth) in every launcher, on TCP 4799, selectable via the connectivity field, first on a Connectivity CRD, later on Link and Topology directly. Its purpose: dodge VXLAN MTU and fragmentation trouble.
Ported to direct Pods anyway (2026-08-19)The direct change first reimplemented it as a sidecar-supervised child process (about 1,700 lines) because the pinned library’s process-global manager could not offer a resettable, race-free reconnect lifecycle inside a Pod.
Deleted the same day, together with the whole in-Pod fabricThe real discovery: kinds that own the Pod’s primary interface (SR Linux renames it and strips its address) leave the namespace without underlay routes, so any transport terminating there dies, VXLAN and TCP alike. The fabric moved to the worker host namespace, and both flavors became aliases of one controller-selected realization. From this moment connectivity: slurpeeth was accepted input that changed nothing.
Interposition dissolves the original problem (2026-08-21)The fabric comes back in-Pod, but on the preserved c9s0 underlay the device can never touch. MTU was clamped below the underlay at this stage (no fragmentation to dodge), and the CNI carries plain Pod-to-Pod UDP wherever Pod traffic works at all.
The selector goes (2026-08-21)The retire change, verbatim: “With slurpeeth retired to an alias of the VXLAN realization, connectivity selected nothing while still constraining behavior (a uint16 VNI clamp, a dead TCP/4799 fabric port) and shipping false CRD prose. The field is removed rather than frozen at a single value; a future second transport should design its own selector.” The dependency left go.mod with the launcher.
The idea returns, done right (2026-08-25)The fabric wire is, in a sense, slurpeeth’s vindication: a userspace transport between sidecars was the right call — but over UDP instead of TCP, so loss stays loss; with carrier and liveness on the same path, so links behave like cables; and as the only transport, so no selector exists. What slurpeeth dodged (MTU trouble) the wire solves head-on by fragmenting to the underlay.
Als Experiment geboren (Dez 2023 bis Jan 2024)Gemerged als Feature-PR #90: ein TCP-Tunnel-Daemon pro Link (carlmontanari/slurpeeth) in jedem Launcher, auf TCP 4799, wählbar über das connectivity-Feld — erst auf einer Connectivity-CRD, später direkt auf Link und Topology. Sein Zweck: VXLAN-MTU- und Fragmentierungsärger ausweichen.
Trotzdem auf Direct-Pods portiert (19.08.2026)Die Direct-Änderung reimplementierte ihn zunächst als sidecar-überwachten Kindprozess (rund 1.700 Zeilen), weil der prozessglobale Manager der gepinnten Bibliothek keinen zurücksetzbaren, race-freien Reconnect-Lifecycle im Pod bot.

Die Fabric zog in den Worker-Host-Namespace, und beide Varianten wurden Aliase einer controller-gewählten Realisierung. Die Interposition löst das ursprüngliche Problem auf (21.08.2026)Die Fabric kommt zurück in den Pod, aber auf dem bewahrten c9s0-Underlay, den das Gerät nie anfassen kann. Die MTU war in dieser Phase unter den Underlay geklemmt (keine Fragmentierung, der man ausweichen müsste), und das CNI trägt schlichtes Pod-zu-Pod-UDP, wo immer Pod-Traffic überhaupt funktioniert.
Der Selektor geht (21.08.2026)Die Retire-Änderung wörtlich: „With slurpeeth retired to an alias of the VXLAN realization, connectivity selected nothing while still constraining behavior (a uint16 VNI clamp, a dead TCP/4799 fabric port) and shipping false CRD prose. Die Idee kehrt zurück — richtig gemacht (25.08.2026)Die Fabric-Leitung ist in gewissem Sinn slurpeeths Rehabilitierung: Ein Userspace-Transport zwischen Sidecars war der richtige Ansatz — aber über UDP statt TCP, damit Verlust Verlust bleibt; mit Carrier und Liveness auf demselben Pfad, damit Links sich wie Kabel verhalten; und als einziger Transport, damit kein Selektor existiert. Was slurpeeth auswich (MTU-Ärger), löst die Leitung frontal: durch Fragmentieren auf den Underlay.
In short: slurpeeth was not removed because it failed. Its removal, and most rows in the table above, follow one rule: the components were not broken, the conditions that required them were removed. And when a condition returned — cross-Pod frames needing userspace handling to escape kernel-tunnel MTU limits — the answer was rebuilt on the lessons learned, not resurrected.

Seine Entfernung — wie die meisten Zeilen der Tabelle oben — folgt einer Regel: Die Komponenten waren nicht kaputt, die Bedingungen, die sie erforderten, wurden entfernt. 09 · Security boundaries
09 · Sicherheitsgrenzen

The powerful parts are small and easy to point at.

Die mächtigen Teile sind klein und leicht zu benennen.

Creating interfaces, routing tables, and NAT rules needs root-like Linux rights. c9s keeps those rights in the fixed clabwire helper. Its normal networking state is Pod-scoped; worker-netns use is bounded to endpoint lifecycle and host-Link duties, and its Kubernetes identity is read-only. The planner and router containers receive neither form of access.

Interfaces, Routing-Tabellen und NAT-Regeln anzulegen braucht root-artige Linux-Rechte. c9s hält diese Rechte im festen Helfer clabwire. Sein normaler Netzwerkzustand ist Pod-begrenzt; die Worker-Netns-Nutzung ist auf Endpoint-Lifecycle und Host-Link-Aufgaben begrenzt, seine Kubernetes-Identität ist read-only. Planner und Router-Container erhalten keinen dieser Zugänge.

Pooled planning worker

It can describe, not launch

No Kubernetes token, host directory, Docker/CRI socket, or privileged networking. Each request gets a fresh process and private scratch on a read-only root filesystem. A default-deny NetworkPolicy isolates workers when the CNI enforces it; the controller supplies external file data.

Planner-Pool-Worker

Er kann beschreiben, nicht starten

Kein Kubernetes-Token, kein Host-Verzeichnis, kein Docker/CRI-Socket, kein privilegiertes Networking. Jede Anfrage bekommt einen frischen Prozess und privaten Scratch bei read-only Root-Dateisystem. Eine Default-Deny-NetworkPolicy isoliert Worker, sofern das CNI sie durchsetzt; externe Dateiinhalte liefert der Controller.

Router container

No Kubernetes identity

automountServiceAccountToken: false. The NOS does not receive cluster credentials, the worker network namespace, or a container-runtime socket.

Router-Container

Keine Kubernetes-Identität

automountServiceAccountToken: false. Das NOS bekommt weder Cluster-Credentials noch den Worker-Netz-Namespace noch einen Container-Runtime-Socket.

Connectivity sidecar

Bounded host and API access

clabwire is privileged for networking. It receives the worker-netns handle needed by imported endpoint hooks and host Links, plus a projected token with namespace-scoped, read-only Link, Pod, and Pod-log permissions. It has no Kubernetes write credentials and talks to no daemon.

Connectivity-Sidecar

Begrenzter Host- und API-Zugriff

clabwire ist für Networking privilegiert. Er erhält den Worker-Netns-Handle für importierte Endpoint-Hooks und Host-Links sowie ein projiziertes Token mit Namespace-begrenzten read-only Rechten für Links, Pods und Pod-Logs. Kubernetes-Schreibrechte und einen Daemon hat er nicht.

The worker

No resident c9s process

No DaemonSet, host socket, or host-network c9s process runs there. The sidecar mounts the worker network-namespace handle read-only, then uses it as the execution context for imported endpoint lifecycle and to place host-Link veth ends. Application containers never receive it.

Der Worker

Kein dauerhafter c9s-Prozess

Dort läuft kein DaemonSet, Host-Socket oder Host-Network-c9s-Prozess. Der Sidecar mountet den Worker-Netz-Namespace-Handle read-only und nutzt ihn als Ausführungskontext für importierten Endpoint-Lifecycle sowie zum Platzieren von Host-Link-veth-Enden. Anwendungscontainer erhalten ihn nie.

The cable ignores placement

Wherever the two Pods land, the cable is a per-Pod veth whose wire leg rides the fabric wire under the Link’s allocated id. r1 and r2 see the same plain 9500-MTU Ethernet interfaces either way — and if one Pod dies, the other’s eth1 shows NO-CARRIER until the replacement converges.

r1-r2

Das Kabel ignoriert die Platzierung

Wo immer die zwei Pods landen: Das Kabel ist ein veth pro Pod, dessen Leitungs-Bein unter der zugeteilten ID des Links auf der Fabric-Leitung fährt. r1 und r2 sehen so oder so dieselben schlichten Ethernet-Interfaces mit MTU 9500 — und stirbt ein Pod, zeigt das eth1 des anderen NO-CARRIER, bis der Ersatz konvergiert.

The whole story in one breath
Die ganze Geschichte in einem Atemzug

Containerlab knows the device. Kubernetes runs it. The sidecar wires it.

Containerlab kennt das Gerät. Kubernetes betreibt es. Der Sidecar verkabelt es.

You create Nodes and Links. c9s reuses a cached plan or sends the Node to a shared planner worker. A fresh process records the Containerlab kind’s decisions, and the controller validates the plan and renders a normal device Pod. Inside that Pod, a privileged sidecar preserves the CNI interface as c9s0, hands the device a synthetic eth0 carrying a controller-allocated management address, routes management traffic between Pods using a projected peer directory, and realizes each cable as a veth pair on the fabric wire: whole frames segmented to the Pod network’s MTU, carrier and heartbeats on the same UDP path, loss kept honest. No c9s daemon or host-network process is installed on workers; clabwire uses an explicit worker-netns handle for imported endpoint hooks and host Links. Containerlab’s own post-start, endpoint, health, and save hooks remain plan-checked. UIDs own the cables; digests own the build; Pod lifetime owns ordinary transport cleanup.

Man erzeugt Nodes und Links. c9s nutzt einen gecachten Plan oder schickt den Node an einen gemeinsamen Planner-Worker. Ein frischer Prozess zeichnet die Entscheidungen des Containerlab-Kinds auf; der Controller prüft den Plan und erzeugt einen normalen Geräte-Pod. In diesem Pod bewahrt ein privilegierter Sidecar das CNI-Interface als c9s0, reicht dem Gerät ein synthetisches eth0 mit controller-zugeteilter Management-Adresse, routet Management-Traffic zwischen Pods anhand eines projizierten Peer-Verzeichnisses und realisiert jedes Kabel als veth-Paar an der Fabric-Leitung: ganze Frames auf die MTU des Pod-Netzes segmentiert, Carrier und Heartbeats auf demselben UDP-Pfad, Verlust bleibt ehrlich. Auf Workern wird kein c9s-Daemon oder Host-Network-Prozess installiert; clabwire nutzt einen expliziten Worker-Netns-Handle für importierte Endpoint-Hooks und Host-Links. Containerlabs PostStart-, Endpoint-, Health- und Save-Hooks bleiben plan-geprüft. UIDs besitzen die Kabel; Digests besitzen den Build; die Pod-Lebenszeit besitzt das gewöhnliche Transport-Cleanup.
