Where does my config live?
Clabernetes persistence, explained for humans.

Wo lebt meine Config eigentlich?
Clabernetes-Persistenz, einfach erklärt.

You configure a router in your lab, type save, and Kubernetes replaces the Pod at 3 a.m. Is your work still there in the morning? With persistence enabled: yes, always. This page explains exactly how — the PVC, the little ledger that makes decisions, saving, resetting, and what happens when you delete things.

Du konfigurierst einen Router im Lab, tippst save, und Kubernetes ersetzt den Pod um 3 Uhr nachts. Ist deine Arbeit am Morgen noch da? Mit eingeschalteter Persistenz: ja, immer. Diese Seite erklärt genau wie — das PVC, das kleine Kassenbuch, das die Entscheidungen trifft, Speichern, Zurücksetzen, und was beim Löschen passiert.

Section 1Abschnitt 1

01The big picture: the PVC is your lab directoryDas große Bild: das PVC ist dein Lab-Verzeichnis

With plain containerlab on your laptop, every lab gets a lab directory on disk. The startup config seeds it once, the router writes its saved config into it, and because the directory survives destroy + deploy, your saved work survives too. Clabernetes does the same thing — but a Pod has no disk of its own, so the lab directory lives on a PersistentVolumeClaim (PVC): a piece of cluster storage with your Node's name on it.

Bei normalem containerlab auf dem Laptop bekommt jedes Lab ein Lab-Verzeichnis auf der Platte. Das startup-config befüllt es einmal, der Router schreibt seine gespeicherte Config hinein, und weil das Verzeichnis destroy + deploy überlebt, überlebt auch deine gespeicherte Arbeit. Clabernetes macht dasselbe — aber ein Pod hat keine eigene Platte, also lebt das Lab-Verzeichnis auf einem PersistentVolumeClaim (PVC): einem Stück Cluster-Storage mit dem Namen deines Nodes drauf.

Persistence OFF (default)Persistenz AUS (Default)

The lab directory is an emptyDir — scratch space that dies with the Pod. Every Pod start is a factory reset to exactly what your YAML declares. Great for CI and demos. Terrible for a lab you work in for days.

Das Lab-Verzeichnis ist ein emptyDir — Schmierzettel, der mit dem Pod stirbt. Jeder Pod-Start ist ein Factory-Reset auf exakt das, was dein YAML deklariert. Super für CI und Demos. Furchtbar für ein Lab, in dem du tagelang arbeitest.

Persistence ONPersistenz AN

One PVC per Node, named after it. The startup config seeds it once; from then on, whatever the device saved wins — across restarts, evictions, node reboots, and unrelated spec changes.

Ein PVC pro Node, nach ihm benannt. Das startup-config befüllt es einmal; ab dann gewinnt, was das Gerät gespeichert hat — über Neustarts, Evictions, Worker-Reboots und fremde Spec-Änderungen hinweg.

# turn it on — that's the whole thing:
spec:
  deployment:
    persistence:
      enabled: true
      claimSize: "5Gi"        # optional, default 5Gi
      storageClassName: "fast"  # optional, default storage class otherwise
Section 2Abschnitt 2

02The cast: who does whatDie Besetzung: wer macht was

Four things cooperate. The controller watches your Node and creates the PVC and the Pod. Inside the Pod, a small prepare init container runs before your router and fills the PVC with the planned files. The device container is the router itself; the kind's directories (for SR Linux: /etc/opt/srlinux) are mounted straight from the PVC. And a tiny file on the PVC, the staging ledger, remembers what prepare wrote — that memory is what makes everything below work.

Vier Dinge arbeiten zusammen. Der Controller beobachtet deinen Node und erzeugt PVC und Pod. Im Pod läuft vor deinem Router ein kleiner Prepare-Init-Container, der das PVC mit den geplanten Dateien befüllt. Der Device-Container ist der Router selbst; die Verzeichnisse des Kinds (bei SR Linux: /etc/opt/srlinux) sind direkt vom PVC gemountet. Und eine winzige Datei auf dem PVC, das Staging-Ledger (Kassenbuch), merkt sich, was Prepare geschrieben hat — dieses Gedächtnis macht alles Folgende erst möglich.

What is in that ledger?Was steht in dem Kassenbuch?

For every file prepare published, a fingerprint (SHA-256 digest) of exactly what it wrote. Plus the last honored reset token, and the list of files it left alone because you changed them:

Für jede Datei, die Prepare veröffentlicht hat, ein Fingerabdruck (SHA-256-Digest) von genau dem, was es geschrieben hat. Plus das zuletzt ausgeführte Reset-Token und die Liste der Dateien, die es in Ruhe gelassen hat, weil du sie geändert hast:

{
  "files": {
    "config/config.json": "sha256:c66fb339…",   ← what prepare last staged there
    "topology.yml":       "sha256:716a92ce…"
  },
  "acknowledgedResetToken": "reset-1",          ← this reset already happened
  "preserved": ["config/config.json"]             ← left alone: the device owns it now
}
Section 3Abschnitt 3

03What happens on every single Pod startWas bei jedem einzelnen Pod-Start passiert

A Pod can be replaced any time — you delete it, a worker reboots, you edit the Topology. Every time, the prepare init container runs first. It re-renders all planned files in a private scratch area and verifies they are byte-for-byte what the plan promised (that check is unchanged — it is the integrity guarantee). New is the second step: instead of blindly copying everything onto the PVC, it now asks the ledger, per file, whether it is allowed to.

Ein Pod kann jederzeit ersetzt werden — du löschst ihn, ein Worker rebootet, du änderst die Topology. Jedes Mal läuft zuerst der Prepare-Init-Container. Er rendert alle geplanten Dateien in einem privaten Arbeitsbereich neu und prüft, dass sie Byte für Byte dem Plan entsprechen (diese Prüfung ist unverändert — sie ist die Integritätsgarantie). Neu ist der zweite Schritt: statt alles blind aufs PVC zu kopieren, fragt er jetzt pro Datei das Ledger, ob er das überhaupt darf.

Section 4Abschnitt 4

04The one rule that decides everythingDie eine Regel, die alles entscheidet

For each planned file, prepare compares three fingerprints: what is on the PVC right now, what the ledger says was staged last time, and what the plan wants to write. One question settles it: “did the device change this file since I last staged it?”

Für jede geplante Datei vergleicht Prepare drei Fingerabdrücke: was gerade auf dem PVC liegt, was laut Ledger zuletzt gestaged wurde, und was der Plan schreiben will. Eine Frage entscheidet: „hat das Gerät diese Datei geändert, seit ich sie zuletzt gestaged habe?“

Why this fixes the old bugWarum das den alten Bug behebt

Before, prepare copied every planned file onto the PVC on every boot, no questions asked. If your startup config produced a real file (an SR Linux JSON config, cEOS flash/startup-config, SR OS cf3/config.cfg, cRPD juniper.conf), your saved config lived at the exact same path — and got silently overwritten with the startup config on the next restart. Hours of work, gone at 3 a.m. The ledger comparison is precisely what was missing.

Vorher kopierte Prepare bei jedem Boot jede geplante Datei aufs PVC, ohne zu fragen. Wenn dein startup-config eine echte Datei erzeugte (SR-Linux-JSON-Config, cEOS flash/startup-config, SR OS cf3/config.cfg, cRPD juniper.conf), lag deine gespeicherte Config auf genau demselben Pfad — und wurde beim nächsten Neustart stillschweigend mit dem startup-config überschrieben. Stunden Arbeit, weg um 3 Uhr nachts. Der Ledger-Vergleich ist genau das, was gefehlt hat.

Section 5Abschnitt 5

05Saving your work — the full round tripDeine Arbeit speichern — die ganze Runde

Saving works like on real hardware: commit to the running config, then save running → startup. You can type the vendor command yourself (tools system configuration save on SR Linux), or run the generic Save lifecycle, which triggers each vendor's own save mechanism — the same verb for every kind. Either way the saved file lands on the PVC, and the ledger rule protects it forever after.

Speichern funktioniert wie auf echter Hardware: committen in die Running-Config, dann running → startup speichern. Du kannst den Hersteller-Befehl selbst tippen (tools system configuration save bei SR Linux) oder das generische Save-Lifecycle laufen lassen, das den Save-Mechanismus des jeweiligen Herstellers anstößt — dasselbe Verb für jedes Kind. So oder so landet die Datei auf dem PVC, und die Ledger-Regel schützt sie ab dann für immer. 

# the generic save, from outside (same command pattern the e2e suite uses):
# take the PostStart command of the device container and swap --phase to Save
kubectl exec <pod> -c <device-container> -- \
  /var/lib/clabernetes/lifecycle-bin/manager node-runtime lifecycle \
  --plan …/plan.json --input …/input.json --phase Save --containerID … --artifacts …

# what you see in the prepare log after the next restart:
preserved device-modified artifact config/config.json for Node …

# and if you save WITHOUT persistence enabled, the save still works but warns:
WARNING: Node … has no persistent artifact volume;
the saved configuration will not survive Pod replacement
Section 6Abschnitt 6

06When you WANT the YAML to win againWenn das YAML doch wieder gewinnen soll

“Saved wins” has a flip side: once a saved config exists, editing the startup-config in your Topology changes nothing on the running node (exactly like containerlab). Two explicit escape hatches put the spec back in charge:

„Gespeichert gewinnt“ hat eine Kehrseite: sobald eine gespeicherte Config existiert, ändert das Editieren des startup-config in deiner Topology nichts am laufenden Node (exakt wie bei containerlab). Zwei explizite Notausgänge geben dem Spec das Kommando zurück:

Permanently: enforce-startup-configDauerhaft: enforce-startup-config

A containerlab node property. When set, the startup config is re-staged on every boot, stomping saved changes at planned paths. For golden-config nodes that must never drift. Declaring it without a startup-config is rejected before anything runs.

Ein containerlab-Node-Property. Gesetzt wird das startup-config bei jedem Boot neu gestaged und überschreibt gespeicherte Änderungen an geplanten Pfaden. Für Golden-Config-Nodes, die nie driften dürfen. Ohne startup-config deklariert wird es abgelehnt, bevor irgendwas läuft.

srl1:
  kind: nokia_srlinux
  startup-config: golden.json
  enforce-startup-config: true

One-shot: the device-state resetEinmalig: der Device-State-Reset

One annotation with a token of your choice. The Pod is replaced, the node's plan-owned files are wiped and re-seeded from the startup config. Each token fires exactly once — the annotation can stay, later saves are safe.

Eine Annotation mit einem Token deiner Wahl. Der Pod wird ersetzt, die plan-eigenen Dateien des Nodes werden gewiped und aus dem startup-config neu geseedet. Jedes Token feuert genau einmal — die Annotation darf bleiben, spätere Saves sind sicher.

kubectl annotate node.c9s.run srl1 \
  c9s.run/device-state-reset=$(date +%s) --overwrite
Section 7Abschnitt 7

07PVC lifecycle: what deleting things actually deletesPVC-Lebenszyklus: was Löschen wirklich löscht

A Pod restart never touches the PVC — that is the whole point. The interesting question is what happens when you delete the Node or the Topology. That is controlled by one field: persistence.reclaim.

Ein Pod-Neustart fasst das PVC nie an — das ist ja der Sinn der Sache. Spannend wird es, wenn du den Node oder die Topology löschst. Das steuert ein einziges Feld: persistence.reclaim. 

spec:
  deployment:
    persistence:
      enabled: true
      reclaim: Retain   # default is Delete

Good to knowGut zu wissen

  • claimSize can grow later, never shrink. The storage class is fixed once the claim exists.claimSize kann später wachsen, nie schrumpfen. Die StorageClass steht fest, sobald der Claim existiert.
  • Disabling persistence deletes the c9s-owned claim — retained (ownerless) claims survive even that.Persistenz ausschalten löscht den c9s-eigenen Claim — behaltene (besitzerlose) Claims überleben sogar das.
  • One claim per Node, ReadWriteOnce, named exactly like the Node: kubectl get pvc srl1.Ein Claim pro Node, ReadWriteOnce, benannt exakt wie der Node: kubectl get pvc srl1.
